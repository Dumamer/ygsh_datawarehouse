## 一、怎么读这份表

| 工作表 | 回答什么问题 |
|---|---|
| 报告说明 | 评估范围、五维度口径定义 |
| 1-完整性 | 哪些字段有空洞？空了多少？（51 个字段全扫） |
| 2-唯一性 | 主键有没有重复？是整行重复还是内容不同？ |
| 3-有效性 | 枚举字段里混进了什么非法值？各多少条？ |
| 4-一致性 | 日期格式统一吗？外键关联得上吗？ |
| 5-准确性 | 年龄、金额这些数字在业务上说得通吗？ |
| 6-清洗效果验证 | 清洗（一）做完后，问题真的解决了吗？ |
| 7-问题清单 | 哪些必须处理、哪些可以放一放、谁在第几周处理 |
| 附录-枚举分布 | 「非法」这个判定依据的全部原始取值 |

> 建议阅读顺序：先看 **7-问题清单** 抓重点，再回 1~5 查细节，最后看 6 验收。

## 二、总体结论

### 2.1 六张表的质量分层

| 档位 | 表 | 判断依据 |
|---|---|---|
| 🟢 干净 | `ods_store`、`ods_order_item`、`ods_user_behavior`(仅枚举)、`ods_product`(仅少量) | 主键唯一、空值极少、外键完整 |
| 🟡 中等 | `ods_user` | 6 个字段有空值，但有 4 个是业务可接受的「有则更好」字段 |
| 🔴 较差 | `ods_order` | 主键重复 3.85%、三个枚举字段非法率 25%~35%、金额有负值和七位数 |

### 2.2 三个最值得讲的问题

**① 订单表 15,600 行里只有 15,000 个真实订单**

- 586 个 `order_id` 出现 2 次，多出 600 行
- 其中 **400 行是十个字段完全相同的整行重复**（典型的数据重复投递）
- 另外 **200 行是 `order_id` 相同但 `pay_amount` 不同**，其中一部分还带着负金额
- **风险**：如果直接 `SELECT COUNT(*)` 出报表，订单量虚高 3.85%；如果去重时随手按时间取一条，可能把负金额那条留下来，GMV 直接算错
- **处理**：`ROW_NUMBER` 按「金额有效性 > 时间新 > 金额大 > 内容兜底」四级排序取第一条（`sql/clean/clean_order_dedup.sql`）

**② 用户表 342 个空值，但只有 2 个字段该"填"**

- `age` 51 个空值 → 中位数填充（**不用均值**：分布右偏 + 存在 150 这种异常值，均值会被拉高）
- `email` 193 个空值 → **保留空值**，只在 DWD 层加一个 `email_is_missing` 标记位。理由：邮箱无法合理推断，编造的邮箱会污染后续营销触达的打开率/退信率统计
- `gender` 84 / `member_level` 14 → 填充为「未知」/「普通会员」，并保留原始标记

**③ 枚举字段是「看起来能用其实不能用」的重灾区**

- `order_status` 有 12 种写法，其中 8 种非法，涉及 5,477 行（35.11%）：`已完成/已支付/已付款/完成/1/2/3/4/cancelled`
- `behavior_type` 10 种写法，非法 47,345 行（78.9%）：`pv/browse/Cart/cart/fav/收藏/加购/buy/购买` 中英混杂
- **风险**：按状态做漏斗、按行为做转化率，口径必然错乱
- **处理**：本周只登记不处理，第 2 周建立映射字典统一为标准值（这是清洗（二）的核心任务）

### 2.3 一个容易被忽略的细节

`ods_product.category` 有 8 个类目名带尾部空格（如 `'图书文娱 '`），
直接 `GROUP BY category` 会把 8 个类目拆成 16 组，看起来"品类变多了"但其实是同一个品类。
本周在补全上架日期时已经用 `TRIM(category)` 规避，第 2 周在 DWD 层统一修掉。

## 三、清洗（一）前后对比

| 检查项 | 清洗前 | 清洗后 | 说明 |
|---|---:|---:|---|
| `dwd_user` 年龄空值 | 51 | **0** | 中位数 40.24 → 填充后全部在 [1,120] |
| `dwd_user` 年龄越界（0 / 150） | 27 | **0** | 与空值一并按中位数重建 |
| `dwd_user` 性别空值 | 84 | **0** | 填充为「未知」 |
| `dwd_user` 会员等级空值 | 14 | **0** | 填充为「普通会员」 |
| `dwd_user` 邮箱空值 | 193 | **193** | 按策略保留，用 `email_is_missing=1` 标记 |
| `dwd_product` 上架日期空值 | 11 | **0** | 按同品类均值回退补全 |
| `dwd_order` 行数 | 15,600 | **15,000** | 减少 600 行 = 预评估发现的多出行数，**PASS** |
| `dwd_order` 重复主键 | 586 | **0** | 唯一性校验通过 |

> 验收口径：**减少的行数必须等于预评估阶段统计出的重复多出行数**，
> 多减了说明误删，少减了说明漏删。本次 600 = 600，PASS。

## 四、还没做、留给第 2 周的部分

| 项 | 记录数 | 为什么本周不做 |
|---|---:|---|
| 枚举标准化（状态/渠道/支付方式/会员等级/性别/行为类型） | 62,354 | 属于「有效性」，需要先和业务对齐标准字典，不是简单替换 |
| 日期格式归一 | 8,115 | 属于「一致性」，要和枚举一起做成统一的清洗规则 |
| 金额/数量异常值处理 | 2,970 | 负金额可能是退款冲正，不能一律删，需要业务确认口径 |
| 手机号格式清洗 | 102 | 影响面小，优先级低 |

本周已在 DWD 层预留标记位（`pay_amount_valid`、`email_is_missing`、`age_is_filled`、`launch_date_is_filled`），
第 2 周的处理可以直接基于标记位做，不用重新扫描全表。

## 五、复现方式

```bash
# 1) 跑完 SQL（建表 -> 导入 -> 校验 -> 质量 -> 清洗）
bash scripts/run_all.sh

# 2) 从 Hive 导出指标（结果即为 docs/quality_raw/*.tsv）
hive -f sql/quality/export_quality_tsv.sql

# 3) 生成 Excel
python scripts/build_quality_report.py
```

> `docs/quality_raw/` 里的 5 个 tsv 是 Excel 的原始输入，已入库，
> 这样即使换台机器，也能直接用 `build_quality_report.py` 复现出完全一致的表格。
