## 一、业务背景

「云购生活」是一家线上线下一体的新零售企业，业务链路为：

```
门店/仓  →  用户下单  →  支付  →  履约  →  售后
              ↓
        线上 APP / 小程序 / PC 官网 / 门店下单
```

数仓需要回答的经营问题：**谁在买（用户）、买什么（商品）、在哪买（门店）、买了多少（订单）、怎么逛的（行为）**。
6 张表正好对应这 5 个问题 + 1 张明细。

## 二、表间关系

```
        ods_user (1000)                ods_product (600)
             │ 1                             │ 1
             │                               │
             │ N                             │ N
        ods_order (15600) ──────1:N──────► ods_order_item (37549)
             │ N                             ▲
             │                               │ N
             │ 1                        ods_user_behavior (60000)
        ods_store (60)                     │ N
                                    ───────┘
```

| 关系 | 说明 | 实测结果 |
|---|---|---|
| `ods_order.user_id → ods_user.user_id` | 每个订单必属一个用户 | 1000 个用户全部有订单，**0  orphans** |
| `ods_order.store_id → ods_store.store_id` | 门店下单可归属门店 | 60 个门店全部被引用，0 orphans |
| `ods_order_item.order_id → ods_order.order_id` | 明细必属订单 | 0 orphans（明细覆盖 15,000 个订单） |
| `ods_order_item.product_id → ods_product.product_id` | 明细必属商品 | 0 orphans |
| `ods_user_behavior.product_id → ods_product.product_id` | 行为必属商品 | 0 orphans |

> 结论：**外键引用完整性良好**，脏数据集中在字段值本身，不在表关联上。

## 五、字段命名与建模约定

1. **贴源层统一 STRING**：不做类型转换，脏数据原样落地（原因见 `sql/ods/create_ods.sql` 文件头注释）。
2. **主键命名**：`<实体>_id`，如 `order_id`、`product_id`。
3. **时间字段**：ODS 层保留原始字符串；DWD 层统一转 `yyyy-MM-dd` / `yyyy-MM-dd HH:mm:ss`。
4. **金额字段**：一律 DOUBLE，单位「元」，保留两位小数；DWD 层增加 `*_valid` 质量标记位。
5. **分层命名**：`ods_` / `dwd_` / `dws_` / `ads_` 前缀区分层次，库名 `ydsh_<层>`。
