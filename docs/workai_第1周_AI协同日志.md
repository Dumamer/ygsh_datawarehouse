## 四、问题与解决

**遇到的问题（按卡点严重度）**

1. Docker 引擎无法启动 → 后续所有「标准化环境」步骤全部阻塞
2. Hive 的 SQL 结果与我用眼睛看到的 CSV 对不上（空值统计全 0）
3. 去重规则不当会误删真实成交金额
4. 生成的 Excel 是空表

**AI 是否有效解决**

- 问题 1：**有效**。AI 没有停在"你重装试试"，而是直接读了 Docker 后端日志，给出 `noVirtualizationReason` 字段，把问题从"玄学"变成"系统功能未启用"这一确定结论。
- 问题 2：**有效且关键**。这是我完全不知道的 Hive 3 版本行为差异，如果没查出来，整份质量报告的空值率会全部是 0。
- 问题 3：**部分有效**。AI 第一版 SQL 语义没错但不合业务，是我发现的，AI 负责按新规则改写。
- 问题 4：**有效**。定位到文件名不匹配，属于低级错误，但需要人打开文件才能发现——AI 自测过脚本"运行成功"，却没验证产物内容。

**最终如何解决**

- 问题 1：改走 JDK 8 + Hadoop 3.1.1 + Hive 3.1.3 原生本地模式，绕开容器；Docker 配置留档，开虚拟机平台后可直接切换。
- 问题 2：统一缺失判定口径 `IS NULL OR TRIM(col) = ''`，并用 Python 独立复算交叉验证。
- 问题 3：把「金额有效性」提到排序第一优先级，并用抽查样例回归验证。
- 问题 4：修正文件名后重新生成，并新增"逐页抽查前 4 行"的自检习惯。

## 五、反思与总结

**AI 协同带来的价值**

- **省掉的是"查文档的时间"，不是"思考的时间"**。Hive 3 的 null 语义、Windows 上 winutils 缺失、MySQL 8 的 `allowPublicKeyRetrieval`，这些细节如果自己踩，每条都要半小时以上。AI 一次给出，我只需验证。
- **把"写代码"的成本压到接近零**，让注意力可以放在"策略是否合理"上。本周我花在"年龄到底用均值还是中位数""去重保留哪一条"的时间，比花在写 SQL 上的时间多——这是好事。
- **排错效率**：Docker 500 错误这种"没有明确报错信息"的问题，AI 直接去读日志文件，比我自己翻设置界面快得多。

**AI 的局限与风险**

- **会"报成功"但产物是错的**。Excel 生成脚本 exit code 是 0，但内容是空表。凡是 AI 说"已完成"，都必须打开产物看一眼。
- **默认实现不一定是业务正确的实现**。去重那版 SQL 语法完全正确、能跑通、行数也对，但保留的记录是错的。**能跑通 ≠ 对**。
- **对版本行为细节会"想当然"**。AI 一开始也按 `IS NULL` 写空值统计，说明它并没有主动想到 Hive 3 的默认值变更，是被数字矛盾逼出来的。
- **依赖风险**：如果整份作业的每一行都是 AI 写的，答辩时被问"为什么用中位数不用均值"就答不上来。所以本周我强制自己：每一个策略决定都写下理由，每一段 SQL 都要求 AI 加中文注释说明意图。

**本次协作中我的能力提升**

- 学会了看 Docker 后端日志定位引擎启动失败，而不是只会 `docker ps` 看结果
- 搞清了 ODS「贴源」到底意味着什么——不是"照抄建表语句"，而是"不对数据做任何隐式转换"
- 理解了窗口函数去重的关键是**排序键的业务含义**，而不是 `ROW_NUMBER` 这个函数本身
- 建立了「AI 给的数字必须用第二种方式复算一遍」的习惯（本周用 Python 交叉验证了 Hive 结果）

**对 AI 协同的改进建议**

1. **先定验收标准，再让 AI 动手**。比如"6 张表行数必须等于数据字典"，先说清楚，AI 就会主动加 `verify_ods.sql`。
2. **让 AI 交代"为什么"**，不只是"是什么"。同样是 `COALESCE(age, avg)`，让它解释为什么不用均值，才能判断它是不是在套模板。
3. **关键数字必须双算**。Hive 算一遍、Python 算一遍，对不上就说明有一边错了——本周靠这一条抓出了两个 bug。
4. **把踩坑过程留下来**。这次的 14 条踩坑记录比最终代码更值钱，第 2 周再遇到同类问题可以直接查表。
